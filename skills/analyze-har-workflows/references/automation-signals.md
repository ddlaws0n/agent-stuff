# Automation signals reference

Use this reference when deciding whether a HAR-observed workflow can be automated and how.

## Automation verdicts

Choose a verdict from the evidence for the user's action, with confidence and unresolved prerequisites:

- **direct-http:** the observed action appears representable as HTTP requests using an available authorized session; no additional acquisition step is identified. Explain any unseen authentication/bootstrap assumptions.
- **http-with-token-refresh:** the implementation needs an acquisition or refresh step for a token, nonce, signed URL, upload ID, or other prerequisite. Identify the source where captured and distinguish observed reuse from proven refresh behavior.
- **browser-assisted:** browser execution is needed or more practical for a demonstrated client-side dependency, signing, or session/challenge flow.
- **manual-only/blocked:** the action has a demonstrated human-only prerequisite or unresolved access challenge. State the blocker without suggesting bypasses.
- **insufficient-evidence:** missing or ambiguous evidence prevents a supported recommendation. Name the missing evidence.

A numeric value may be a nonce and a UUID may be a stable resource ID. Appearance, equality, and one successful action cannot establish lifetime or safe replay. Challenge scripts elsewhere in the capture do not prove that the action requires a challenge. Distinguish headers observed in a request from headers proven necessary.

## Common workflow archetypes

### Classic HTML form

Signals:

- `GET` document page returns HTML with hidden inputs.
- `POST` form-urlencoded or multipart body.
- Response is `302` redirect or HTML success page.

Automation approach:

1. `GET` form page.
2. Parse hidden fields and CSRF token.
3. Submit `POST` with session cookies and fields.
4. Follow redirect and verify success marker.

### JSON API action

Signals:

- `fetch`/`xhr` request with JSON body.
- Same-origin `/api`, `/v1`, `/v2`, `/rest`, or domain-specific API path.
- Response includes created/updated resource, ID, status, or validation errors.

Automation approach:

1. Authenticate or reuse a session cookie only with permission.
2. Fetch bootstrap config if required.
3. Send JSON payload with required headers.
4. Verify response and optionally fetch resource by ID.

### GraphQL mutation

Signals:

- URL often `/graphql` or equivalent.
- JSON body has `operationName`, `query`, and `variables`.
- Mutation name appears in query text.

Automation approach:

1. Group by `operationName`.
2. Identify required variables and dynamic IDs.
3. Recreate the mutation body.
4. Preserve headers used for CSRF/session if required.

### Upload flow

Signals:

- `multipart/form-data` request, `blob`, `arraybuffer`, or binary mime type.
- Requests to S3/GCS/Azure storage, presigned URL, or CDN/storage host.
- Separate calls named `init`, `presign`, `complete`, `attach`, `process`, or `status`.

Automation approach:

1. Call initiation endpoint to get upload ID or presigned URL.
2. Upload bytes to storage endpoint with exact method/headers required by signature.
3. Call complete/attach endpoint.
4. Poll processing/status endpoint until success.

### Settings/profile change

Signals:

- `PATCH`, `PUT`, or `POST` to `/settings`, `/profile`, `/account`, `/users/{id}`.
- May require CSRF or ETag/If-Match concurrency headers.
- Response may be `204 No Content`.

Automation approach:

1. Fetch current settings to capture IDs, ETag, CSRF, and current field names.
2. Submit minimal patch when possible.
3. Verify by fetching settings again.

## Dynamic value checklist

Look for these before calling an endpoint replayable:

- Session cookies: cookie names, SameSite behavior, domain scope, expiry.
- Authorization: bearer token, refresh flow, token source.
- CSRF: header or body field, source page/API, one-time or session-scoped.
- Nonce/timestamp/signature: one-time or generated by JS.
- Resource IDs: user ID, tenant ID, workspace ID, organization ID, record ID.
- Optimistic concurrency: `ETag`, `If-Match`, version, revision, updatedAt.
- Upload IDs: presigned URL, upload session ID, object key, content hash.
- Locale/tenant headers: organization, workspace, region, environment.

## Confidence guide

- High confidence in the workflow explanation: relevant request and response bodies are available, dynamic values are traced to earlier requests, and a verification request confirms the result. This does not prove future replay or refresh behavior.
- Medium confidence: primary request is clear but some token/bootstrap details need live testing.
- Low confidence: relevant requests are missing/truncated, task timing is unclear, or the workflow uses sockets/challenges not captured in HAR.

## Redaction rules

Replace these values with placeholders in reports and code examples:

- `Authorization`, `Cookie`, `Set-Cookie`, `X-CSRF-*`, `X-XSRF-*`, API keys, tokens, JWTs, session IDs.
- Passwords, OTPs, MFA codes, payment details, full uploaded file contents.
- Personal data unless necessary to explain field shape; prefer examples like `<email>` or `<display-name>`.
