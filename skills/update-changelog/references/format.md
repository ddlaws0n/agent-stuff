# Changelog format and evidence

## Generator indicators

If any of these exist and the tool writes the changelog, it owns the file. Also treat a header such as "generated by" or "do not edit" as ownership.

| Tool | Files and CI |

Search CI beyond `.github/workflows`: `.gitlab-ci.yml`, `.circleci/config.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `.buildkite/`, `Jenkinsfile`.

## New file (Keep a Changelog 1.1.0)

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]
```

Add the `[Unreleased]` link definition (see Compare links) once a release tag exists; with no tag, leave the heading as plain text. Drop the Semantic Versioning sentence if the project does not use it. Do not backfill history unless asked.

## Evidence commands

- Last release: `git describe --tags --abbrev=0 --match 'v[0-9]*'` (adjust the match to the existing tag prefix, or none). List tags with `git tag --sort=-v:refname`.
- No tags: use `git log HEAD` (a `<root>..HEAD` range would omit the root commit) and say the range covers all history.
- Commits: `git log --no-merges --format='%h %s' <base>..HEAD`; add `--merges` or `--first-parent` to see merge-commit pull requests.
- Pull requests (optional): `gh pr list --state merged --base <branch> --limit 200 --search "merged:>=<tag date>" --json number,title,body,labels,url`. `gh` stops at `--limit`; if you get exactly that many, narrow the date window and repeat. Without `gh` or network access, use commits only and say so.
- Shallow clone (`git rev-parse --is-shallow-repository` prints `true`): run `git fetch --unshallow --tags` if the user allows, otherwise report that the range may be incomplete.
- Release or backport branches: use the latest tag reachable from the branch being changelogged, not the highest tag in the repository. Skip cherry-picks whose entry already exists under another version.
- Squash merges put the PR number in the subject (`(#123)`), merge commits in the merge message; match on that number to avoid double entries.

## Compare links

The version in a heading must match the tag, including its prefix (`v1.4.0` or `1.4.0`). Build links from `git remote get-url origin` after normalizing SSH and HTTPS forms.

<!-- prettier-ignore -->
| Host | Compare | First release |
|-|-|-|
| GitHub | `https://github.com/OWNER/REPO/compare/v1.3.0...v1.4.0` | `https://github.com/OWNER/REPO/releases/tag/v1.0.0` |
| GitLab | `https://gitlab.com/OWNER/REPO/-/compare/v1.3.0...v1.4.0` | `https://gitlab.com/OWNER/REPO/-/tags/v1.0.0` |

Self-hosted GitHub Enterprise and GitLab use the same paths on the instance host. For other hosts, copy the form already used in the file or ask the user.

After a cut, the link block reads, newest first:

```markdown
[Unreleased]: https://github.com/OWNER/REPO/compare/v1.4.0...HEAD
[1.4.0]: https://github.com/OWNER/REPO/compare/v1.3.0...v1.4.0
```

## Prereleases

Use SemVer identifiers in the heading and tag (`## [1.5.0-rc.1] - 2026-10-25`). Compare a prerelease against the previous tag in the same line, whether prerelease or stable. When the stable release ships, follow what the file already does: keep prerelease sections and add the stable one, or fold them into one `[1.5.0]` section. If the file has no precedent, keep them and tell the user.
