# Manage Orca workspaces

## Workflow

1. Establish scope. Identify the repository, PRs, Run home, queue parent, and whether the user wants an audit or changes. Resolve the session CLI per the installed Orca discovery stub. In the commands below, replace `ORCA` with that executable. Load `ORCA skills get orca-cli` and `ORCA skills get orchestration`. Inspect `ORCA agent-context --json` and command-specific help for installed flags. Apply the live guides for placement, recovery and version differences.
2. Inventory before acting. Read `ORCA orchestration run-current` and `ORCA orchestration run-list`; inspect the candidate with `ORCA orchestration run-show --id <run>`, `ORCA orchestration task-list --run <run>` and `ORCA orchestration worker-list --run <run>`. Use JSON, follow pagination, and pin every command to its intended environment. For each full PR URL, use `ORCA reference find <url> --repo <selector> --json`, then inspect exact worktree identity, parent, links, branch and workers. Check the forge for repository, PR number, base, head SHA, draft/open/merged/closed state, review and checks. For a bot queue, record the item ID, observed PR URL, owner and latest handoff from the supplied item or chat. Cross-check these against the forge and dispatch. The bot item and workspace can have different statuses. Starting a worker with `--item` from the bot’s own chat also moves the item to In progress; avoid a duplicate start to repair a stale column. Verify the checkout HEAD and local changes, including staged and untracked files, with read-only Git commands. Flag stale links, duplicate candidates, inaccessible data and mismatched heads.
3. **Audit only:** Return the queue and proposed actions here. Use read-only inventory, including `ORCA orchestration inbox` if message history is needed. A normal mailbox `check` can consume messages. Leave Run binding, tasks, references, columns, terminals, worktrees and Git state untouched.
4. For execution, reuse the identified queue Run. If none exists, use `ORCA orchestration run-create --environment local --objective "<queue>" --json` on a local Run home. Record the returned Run ID and pass it wherever supported. Group PR workspaces beneath the designated queue parent. For an authorized existing child, use `ORCA worktree set --worktree <child> --parent-worktree <parent> --json` after checking the prior parent. Resolve conflicting ownership before reparenting. Grouping is Orca metadata and does not establish a Git base or dependency. Leave the primary checkout, unrelated children, commits and local work intact.
5. Route fixes to the existing owner with `ORCA orchestration send --to dispatch:<id> --subject "<PR>" --body "<bounded follow-up>"`. Read the receipt: local settled workers can receive a new Task even after release. For a settled paired-server worker follow the placement guide. When no worker owns the work, use `ORCA orchestration worker-start` on the exact existing PR worktree. For a missing workspace start from the verified queue parent using `ORCA orchestration worker-start --environment local --run <run> --worktree new-child --name <name> --base-branch <verified-ref> --agent <agent> --spec-file <brief> --json`. Verify the chosen ref resolves to the intended starting SHA and establish how edits will reach the PR head before assigning writes. Include the PR URL, branch, scope, dependencies and expected evidence. Record returned task, dispatch and worktree IDs. Follow receipt recovery on an ambiguous start to avoid duplicate assignments.
6. Link the verified PR with `ORCA reference add <full-pr-url> --worktree <child> --json` when missing. Confirm with `ORCA reference list --worktree <child> --json`. Preserve other references. When asked to reconcile the Orca board, check configured column IDs and team conventions. For example, an assigned implementation can move to `in-progress`, a PR awaiting review to `in-review`, and a merged PR with all scoped work accepted to `completed`. Closed-unmerged, failed, blocked and unknown cases need an explicit disposition. Set only a verified mismatch with `ORCA worktree set --worktree <child> --workspace-status <id> --json`. Re-read the workspace and report the observed result. Treat external project boards as a separate scope.
7. On each Orca wake, handle questions, failures and completion receipts for the matching dispatch. Verify evidence against the current PR head before accepting the result. A successful worker report settles its task even if the PR is open. A merge does not settle a running worker. For cleanup, inspect `ORCA orchestration worker-show --dispatch <id>` and fresh `ORCA orchestration worker-list --run <run> --json` resource accounting. Honor user keep-open, pending follow-ups and custody. Allow scheduled automatic release; for requested cleanup of an eligible settled dispatch use `ORCA orchestration worker-release --dispatch <id> --json`. Inspect the disposition even on exit zero: retained and pending are possible. Follow the receipt for uncertain release. Silence, an idle pane and an old completion message do not establish present eligibility. Leave active or uncertain workers, user sessions, worktrees and branches in place.

## Output

Report one row per PR with URL/head, workspace identity and parent, actual board column, Run/task/dispatch and worker outcome, verified evidence, and next action or blocker. Identify proposed versus confirmed changes and any retained resources. For a queue-wide conclusion, account for each PR including those with missing workspaces or unavailable forge data.
